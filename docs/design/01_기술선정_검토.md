작성 2026-10-22 · 기준 환경 Windows 11 (26200) · .NET 9 SDK · Claude Code 2.1.307

처음 받은 기술 검토 보고서(C#·Go·TypeScript·Python 비교)를 다시 읽고, 이 PC에서 직접 확인한 내용을 덧붙였습니다.
결론은 보고서와 같습니다. 다만 몇 군데는 설계가 더 단순해지거나 위험이 더 크다고 판단해 순서를 바꿨습니다.

## 보고서에 덧붙인 것

### 1. 대화 재개는 앱이 세션 ID를 먼저 정하면 끝납니다

설치된 CLI(`claude --help`)에 `--session-id <uuid>` 가 있습니다.
앱이 UUID를 만들어 `--session-id` 로 첫 실행을 하고, 다음 기동 때 같은 값으로 `--resume` 합니다.
CLI 출력에서 ID를 읽어 낼 필요가 없어서, 보고서에서 3단계로 잡았던 복원을 1단계에 같이 넣었습니다.

주의할 점이 하나 있습니다. 세션을 띄우기만 하고 아무 말도 하지 않으면 대화 파일이 생기지 않습니다.
그 상태에서 `--resume` 하면 실패하기 때문에, 앱은 `~/.claude/projects/*/<ID>.jsonl` 이 있고 비어 있지 않을 때만 재개합니다.

`--name` 으로 탭 이름도 함께 넘깁니다. Claude 입력칸 테두리와 `/resume` 목록에 같은 이름이 보입니다.

### 2. 상태 표시(Hook)는 세션마다 `--settings` 로 주입합니다

사용자의 `~/.claude/settings.json` 을 고치지 않습니다. 앱이 띄운 세션에만 Stop·Notification Hook 이 붙고,
Hook 은 named pipe 로 앱에 알립니다. 4단계에서 만듭니다.

### 3. 프로세스 정리는 Job Object 가 맡습니다

보고서는 "PTY 프로세스 정리 누락"을 위험으로만 적었습니다.
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 로 묶어 두면 앱이 강제 종료돼도 OS가 자식과 손자 프로세스를 함께 끝냅니다.
프로세스를 일시정지 상태로 만들고 Job 에 넣은 다음 깨웁니다. 그래야 깨어나자마자 띄운 손자까지 빠짐없이 묶이기 때문입니다.

### 4. 한글 입력이 가장 큰 미확인 위험이었습니다

xterm.js 와 WebView2 조합은 한글 조합 중 글자 표시가 어긋나는 사례가 있습니다.
그래서 1단계 수용 기준에 넣었습니다. 확인한 범위는 아래 "1단계 확인 결과"에 적었습니다.
안 되면 대안은 `Microsoft.Terminal.Wpf`(Windows Terminal 렌더러) 컨트롤입니다.

### 5. WebView2 는 하나만 둡니다

세션마다 WebView2 를 따로 두면 브라우저 렌더러가 늘어납니다. 하나에 xterm 인스턴스를 여러 개 두는 쪽이 확실히 가볍습니다.
보고서에 있던 "하나 vs 패널별" 비교는 우선순위를 낮췄습니다.

### 6. Windows Terminal 과 무엇이 다른가

이름 있는 탭, 화면 분할, 폴더별 프로필은 Windows Terminal 도 됩니다. 이 앱이 따로 있어야 하는 이유는 세 가지입니다.

- 세션 ID 를 앱이 들고 있어서, 앱을 다시 켜면 탭마다 **같은 대화로** 이어집니다
- 어느 세션이 입력을 기다리는지, 끝났는지를 목록에서 바로 봅니다(4단계)
- 나중에 Codex·Gemini CLI 를 같은 목록에서 다룹니다(5단계)

### 7. 남은 판단

- Tauri 의 경량화 점수(5)가 C#(4)보다 높게 매겨져 있지만, Windows 에서는 Tauri 도 WebView2 를 씁니다. C# 에 WebView2 를 붙이면 런타임이 같아서 차이는 거의 없습니다. 순위는 바뀌지 않습니다.
- 운영체제에 들어 있는 ConPTY 대신 NuGet `Microsoft.Windows.Console.ConPTY` 를 같이 배포하면 화면 크기 변경과 TUI 렌더링이 나아질 수 있습니다. 2단계(분할·크기 변경)에서 비교합니다.
- 참고 오픈소스 4개(AIAgentPersistentTerminal·ClaudeTerminal·CCSM·Shellboard)는 아직 코드를 열어 보지 않았습니다. 가져다 쓰기 전에 라이선스와 유지 상태를 확인합니다.

## Monaco 에디터를 바탕으로 쓰지 않는 이유

Monaco 는 코드 편집기입니다. VS Code 안의 터미널도 Monaco 가 아니라 xterm.js 입니다.
Monaco 에서 출발해도 PTY·ANSI 렌더링·탭은 결국 xterm.js 와 ConPTY 로 다시 만들어야 합니다.

| 방식 | 판단 |
|---|---|
| VS Code(Code-OSS) 포크 | 쓰지 않습니다. Electron 위에 확장 호스트까지 올라가 빈 창부터 무겁습니다 |
| Monaco 만 WebView2 에 넣기 | 터미널로는 쓰지 않습니다. diff 보기·설정 파일 편집 같은 보조 기능으로는 후보입니다 |

보조 기능으로 넣는다면 세 가지를 지킵니다. 이미 떠 있는 WebView2 안에서 열고, 열 때만 읽어 들이고, 인스턴스는 하나만 둡니다.
그러면 평소 터미널만 쓸 때의 메모리는 그대로입니다. 5단계 확장 후보로 둡니다.

### ConPTY NuGet 비교는 하지 않았습니다

보고서는 2단계에서 운영체제 내장 ConPTY 와 NuGet 판을 비교하자고 했습니다.
내장 ConPTY 로 위 크기 변경을 모두 통과했기 때문에 비교를 미뤘습니다. 화면이 깨지는 사례가 나오면 그때 비교합니다.

### 이번 단계에서 고친 성능 문제 둘

1. **세션 시작이 UI 스레드를 막았습니다.** 4칸을 한꺼번에 띄우면 세션 하나에 0.5~0.9초씩 차례로 걸려(그중 대화 기록 조회 70~180ms) 2.1초 동안 네 칸의 화면이 모두 멈췄습니다.
   시작을 스레드풀로 옮긴 뒤에는 claude 4개가 0.1초 안에 함께 뜹니다. 띄우는 사이의 경계(첫 출력, 곧바로 끝나는 프로세스, 중복 시작)는 시험 4건으로 막아 두었습니다.
2. **가상 호스트 `msm.local` 이 페이지를 2초 늦췄습니다.** HTML 은 69ms 에 왔는데 하위 파일 요청이 2,044ms 에 시작했습니다. `.local` 은 mDNS 이름 조회 대상이기 때문입니다.
   `msm.example` 로 바꾼 뒤 페이지 준비가 2.2초에서 0.7~1.3초로 줄었습니다.

### 남은 기동 시간

이 PC 에서 쓸 수 있게 될 때까지 7~11초입니다. 구간은 .NET 기동 2.9~5.9초, 창 구성 약 1초, WebView2 1.9~3.0초, 페이지 0.7~1.3초입니다.
ReadyToRun 게시본도 .NET 기동이 약 3.1초로 같아서 넣지 않았습니다. 측정하는 동안 이 PC 에 다른 claude 세션 여러 개가 돌고 있어 값이 흔들렸습니다. 3단계에서 다른 환경과 비교합니다.
